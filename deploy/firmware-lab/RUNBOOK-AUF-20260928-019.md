# Runbook: Deploy CADS-DEMO-firmware-lab (next, PR #3) auf `service`

Auftrag: AUF-20260928-019. Ausführung durch `Cads_MCTO_service`. **Deploy erst nach
ausdrücklicher Freigabe des CTO (S).**

## 0. Korrekturen gegenüber der ursprünglichen Auftragsnote

Vor der Freigabe offenzulegen (konservative Stimme der Debatte):

1. Es gibt auf `service` keinen Container `firmware-lab-34a13a96`. Der Container heißt
   `firmware-lab` (Default von `deploy.sh`, siehe `.env.example`). `34a13a96` ist vermutlich
   die Tunnel-/ct-agent-Instanz, nicht der Container.
2. Das Ziel-Image ist **nicht** `next@1c68caf`. Laut Rückfrage beim CTO (Vault `b157eca`)
   wird `next` **nach Merge von PR #3** deployt (der PR behebt einen Cache-Fehler im
   Seed-Layer). Der SHA steht erst nach dem Merge fest. Dieses Runbook nimmt ihn deshalb
   als Parameter (`SHA`, `TAG`), nicht als festen Wert. Vorprüfung heißt hier: Image-CI
   grün **für diesen SHA** und der Tag **für genau diesen SHA** in ghcr vorhanden — nicht
   irgendein `next`-Tag.
3. Auf `service` existiert weder `deploy/` noch `.env`; der dortige Checkout kennt
   `deploy.sh`/`smoke.sh` nicht. Schritt 0 unten holt `deploy/` nach; `.env` entsteht aus
   dem Secret-Bestand des Hosts bzw. aus dem laufenden Container (Schritt 0b), nie aus
   diesem Dokument.

Größtes Risiko: **Plattenplatz**. `service` hat 3,8 GB frei bei 94 % Auslastung. Ein Pull
des neuen Images (~1 GB Download, ~3,8–4 GB entpackt) plus eine Sicherung auf demselben
Host können das knapp machen; ein volles Root-Dateisystem nimmt das laufende Labor mit.
`deploy.sh` prüft den Platz vor dem Pull selbst (siehe unten, Schritt 3) und bricht ohne
Änderung ab, wenn es nicht reicht — die Sicherung in Schritt 4 (Option B) gehört deshalb
auf einen **anderen Host**, oder muss vor dem Pull laufen und danach nachgemessen werden.

## Entscheidung für den CTO: Umgang mit dem Workspace-Volume

Der Seed (öffentliches `scimbe/cads-zero-firmware`, `praktikum/start`, ohne Token) greift
nur bei **leerem** Workspace. Die laufende Interims-Instanz behält ihren alten
`cads-lab`-Workspace, solange das Volume `firmware-lab-workspace` bestehen bleibt.

- **Option A — Volume behalten.** Kein Datenverlust, aber kein automatischer Seed;
  Studierende legen `cads-zero` manuell an oder holen es selbst. Rückweg: entfällt, es
  ändert sich nichts am Volume.
- **Option B — Volume sichern, dann leeren/neu anlegen.** Erst Stream-Sicherung auf einen
  anderen Host (Schritt 4), dann `docker volume rm` + `docker volume create` desselben
  Namens, danach seedet das Image beim nächsten Start automatisch. **Achtung:** im Volume
  können fremde Nutzerdaten liegen (Interimsbetrieb) — Option B nur mit angefertigter und
  geprüfter Sicherung und nur mit ausdrücklichem Wort des CTO ausführen.

Dieses Runbook trifft die Wahl A/B nicht selbst; die betreffenden Schritte sind markiert
und werden nur bei expliziter Freigabe von Option B ausgeführt.

## Nicht anfassen

Das Volume `cads-demo-firmware-lab_firmware-lab-workspace` ist ein Überbleibsel (vermutlich
aus einem früheren compose-Setup) und **wird in diesem Runbook nicht angefasst** — nicht
gelesen, nicht gemountet, nicht gesichert, nicht gelöscht.

## Parameter

```bash
# SHA ist der 7-stellige Kurz-SHA, wie ihn CI im Tag next-<sha7> verwendet.
# Laut Auftragsnote (heute: AUF-20260929-021) ist der aktuelle Zielstand:
SHA="54cb23d"
TAG="next-${SHA}"   # heute: next-54cb23d
REPO="ghcr.io/scimbe/cads-firmware-lab"
DATUM="$(date +%Y%m%d)"
ROLLBACK_TAG="rollback-${DATUM}"
```

Alle folgenden Befehle laufen auf `service`, im Verzeichnis `deploy/firmware-lab/` des
Checkouts aus Schritt 0, sofern nicht anders angegeben.

## Schritt 0 — `deploy/` am Deploy-Commit auschecken

```bash
ssh service '
  set -e
  cd /opt/cads-demo-firmware-lab   # bestehender Checkout auf service
  git fetch origin
  git checkout "'"$SHA"'" -- deploy/firmware-lab
'
```

`$SHA` ist hier derselbe Commit, aus dessen Build `TAG` stammt (next nach Merge von PR #3);
damit stimmen ausgecheckte Skripte und deployter Image-Tag überein.

## Schritt 0b — `.env` anlegen

`.env` entsteht **innerhalb eines Befehls** entweder aus dem Secret-Bestand von `service`
oder per `docker inspect` des laufenden Containers — nie aus Chat, Repo oder Transkript,
und ohne den Inhalt auszugeben:

```bash
ssh service '
  set -e
  cd /opt/cads-demo-firmware-lab/deploy/firmware-lab
  umask 077
  {
    docker inspect firmware-lab --format "{{range .Config.Env}}{{println .}}{{end}}" \
      | grep -E "^(PASSWORD|TUTOR_LLM_BASE_URL|TUTOR_LLM_API_KEY|TUTOR_LLM_MODEL)=" \
      | sed "s/^PASSWORD=/FIRMWARE_LAB_PASSWORD=/"
    printf "FIRMWARE_LAB_CONTAINER=firmware-lab\n"
    printf "FIRMWARE_LAB_VOLUME=firmware-lab-workspace\n"
    printf "FIRMWARE_LAB_TAG=%s\n" "'"$TAG"'"
  } > .env
  chmod 600 .env
  test -s .env && echo ".env angelegt ($(wc -l < .env) Zeilen)"
'
```

`FIRMWARE_LAB_CONTAINER=firmware-lab` und `FIRMWARE_LAB_VOLUME=firmware-lab-workspace`
entsprechen den Defaults von `deploy.sh` und werden hier nur explizit gemacht, nicht
geändert. Kein Befehl in diesem Runbook gibt `.env`, das Passwort oder den API-Schlüssel
aus (kein `cat .env`, kein `echo $FIRMWARE_LAB_PASSWORD`).

## Schritt 1 — Vorprüfung: CI grün, Tag in ghcr

**Vorbedingung:** Image-CI muss für genau den SHA aus der Auftragsnote grün sein, bevor
Schritt 2 beginnt — heute (AUF-20260929-021) also für `SHA=54cb23d` (`TAG=next-54cb23d`).
Die sha256sum-Syntax in Schritt 4 wurde nicht gegen die coreutils-Version von `service`
geprüft; das prüft `Cads_MCTO_service` vor der Ausführung.

```bash
# Image-CI (amd64+arm64) für genau diesen SHA grün:
gh run list --repo scimbe/CADS-DEMO-firmware-lab --commit "$SHA" --json workflowName,conclusion

# Tag in ghcr für genau diesen SHA vorhanden (kein anderer next-Tag genügt):
docker manifest inspect "${REPO}:${TAG}" >/dev/null \
  && echo "ok: ${REPO}:${TAG} in ghcr" \
  || { echo "FEHLT: ${REPO}:${TAG} nicht in ghcr - nicht deployen"; exit 1; }
```

Beides muss grün sein, bevor Schritt 2 beginnt. Ohne beides: abbrechen, nicht deployen.

## Schritt 2 — Rollback-Tag setzen (vor jeder Änderung)

```bash
ssh service '
  set -e
  RUNNING_REF="$(docker inspect firmware-lab --format "{{.Config.Image}}")"
  echo "aktuell laufend: $RUNNING_REF"   # heute: '"$REPO"':next-895faf3
  docker tag "$RUNNING_REF" "cads-firmware-lab:'"$ROLLBACK_TAG"'"
  docker image inspect "cads-firmware-lab:'"$ROLLBACK_TAG"'" >/dev/null \
    && echo "Rollback-Tag geprüft: cads-firmware-lab:'"$ROLLBACK_TAG"'" \
    || { echo "FEHLER: Rollback-Tag existiert nicht - abbrechen"; exit 1; }
'
```

**Rollback-Tag für dieses Deployment: `cads-firmware-lab:${ROLLBACK_TAG}`** — in den
Auftrag zurücktragen, sobald ausgeführt.

## Schritt 3 — Platz schaffen, nachmessen

Bezug: INC-008 (voller Host nimmt das laufende Labor mit). Alte `cads-firmware-lab`-Tags
entfernen, außer dem laufenden und dem gerade gesetzten Rollback-Image:

```bash
ssh service '
  set -e
  RUNNING_REF="$(docker inspect firmware-lab --format "{{.Config.Image}}")"
  docker images --format "{{.Repository}}:{{.Tag}}" \
    | grep "^'"$REPO"':" \
    | grep -v -F "$RUNNING_REF" \
    | xargs -r -n1 docker image rm
  df -h "$(docker info --format "{{.DockerRootDir}}")"
'
```

`docker image rm` selbst verweigert nichts wegen anderer Tags — der Befehl entfernt nur die
angegebene Tag-Referenz und löscht die zugrunde liegenden Layer erst, wenn kein Tag und kein
Container mehr darauf zeigt. Der Schutz hier entsteht vorher, durch die Filterung: das
laufende Image ist per `grep -v -F "$RUNNING_REF"` von der Kandidatenliste ausgeschlossen,
und der Rollback-Tag `cads-firmware-lab:${ROLLBACK_TAG}` läuft unter einem eigenen, lokalen
Repository-Namen (aus Schritt 2) und wird von `grep "^$REPO:"` gar nicht erst erfasst — beide
tauchen deshalb nie in der Liste auf, die an `docker image rm` geht.
`df -h` danach zeigt, ob der Pull in Schritt 5 jetzt passt; `deploy.sh` prüft das vor dem
Pull ohnehin selbst und bricht ohne Änderung ab, wenn nicht.

## Schritt 4 — nur bei Option B: Volume sichern

**Nur ausführen, wenn der CTO Option B ausdrücklich freigegeben hat.** Sicherung per
Stream auf einen **anderen Host** (nicht `service` — Plattenrisiko), mit sha256 und
Zielort:

```bash
BACKUP_HOST="<anderer Host, nicht service>"
BACKUP_PATH="/srv/backups/firmware-lab-workspace-${DATUM}.tar"

# 1. Stream vollständig und synchron auf den Zielhost schreiben, danach den Exit-Code
#    prüfen - kein 'tee >(ssh ...)': die Shell wartet eine Process-Substitution nicht ab,
#    ein Abbruch oder eine unvollständige Übertragung im ssh-Zweig würde die Pipeline sonst
#    unbemerkt "erfolgreich" erscheinen lassen, sichtbar erst bei der Wiederherstellung.
set -o pipefail
ssh service "
  docker run --rm -v firmware-lab-workspace:/vol:ro alpine tar -C /vol -cf - .
" | ssh "$BACKUP_HOST" "cat > '$BACKUP_PATH'"
test $? -eq 0 \
  || { echo "FEHLER: Stream fehlgeschlagen - abbrechen, nicht prüfen, nicht fortfahren"; exit 1; }

# 2. Erst nach vollständigem, geprüftem Upload: Prüfsumme auf dem Zielhost aus der dort
#    liegenden Datei erzeugen (Format '<sha256><zwei Leerzeichen><pfad>', mit
#    'sha256sum -c' prüfbar) und sofort verifizieren. Beispielzeile:
#    3b1fe4b9c2a7d1e5f6a8b0c9d2e4f6a8b0c9d2e4f6a8b0c9d2e4f6a8b0c9d2e4  /srv/backups/firmware-lab-workspace-20260929.tar
ssh "$BACKUP_HOST" "
  set -e
  sha256sum '$BACKUP_PATH' > '${BACKUP_PATH}.sha256'
  sha256sum -c '${BACKUP_PATH}.sha256'
"
```

Zielort und Prüfsumme: `${BACKUP_HOST}:${BACKUP_PATH}` (+ `.sha256`) — in den Auftrag
zurücktragen. Erst danach, und nur mit dem Wort des CTO:

```bash
ssh service '
  set -e
  docker rm -f firmware-lab-workspace-check 2>/dev/null || true
  docker volume rm firmware-lab-workspace
  docker volume create firmware-lab-workspace
'
```

Ohne Freigabe von Option B: diesen Schritt und die Volume-Neuanlage überspringen
(Option A), direkt zu Schritt 5.

## Schritt 5 — Deploy

```bash
cd deploy/firmware-lab   # Checkout aus Schritt 0, auf service
./deploy.sh --tag "$TAG" --dry-run
./deploy.sh --tag "$TAG"
```

`deploy.sh` pinnt seinen eigenen Rollback-Kandidaten aus dem gerade laufenden Container und
löst bei fehlgeschlagenem Health-Check bzw. `smoke.sh` **automatisch** ein Rollback aus
(siehe Rückweg unten) — der in Schritt 2 gesetzte Tag ist die von diesem Runbook
dokumentierte, zusätzliche Sicherung desselben Standes.

## Schritt 6 — Smoke-Test

```bash
./smoke.sh
```

Muss mit `PASS: firmware-lab smoke test` enden.

## Schritt 7 — Nachweis: Digest von `$TAG` läuft

Das Image-CI baut amd64+arm64, `${REPO}:${TAG}` ist also ein Multi-Arch-Manifest (Index).
`docker manifest inspect | grep digest` zeigt dabei die Digests der einzelnen
Plattform-Manifeste, nicht zwingend den Index-Digest, gegen den `RepoDigests` aus
`docker inspect` verglichen werden muss (abhängig vom Docker-Storage-Treiber kann das sonst
falsch-negativ wirken). Für den Vergleich deshalb den Index-Digest gezielt ziehen:

```bash
ssh service '
  docker inspect firmware-lab --format "{{index .RepoDigests 0}}"
'
docker buildx imagetools inspect "${REPO}:${TAG}" --format '{{.Manifest.Digest}}'
```

Der Digest aus `docker inspect firmware-lab` (der Teil nach `@sha256:` im `RepoDigest`) muss
dem Index-Digest aus `docker buildx imagetools inspect` entsprechen. Beide Werte in den
Auftrag zurücktragen.

## Rückweg (Rollback)

- **Automatisch:** Schlägt Health-Check oder `smoke.sh` in Schritt 5/6 fehl, rollt
  `deploy.sh` selbst auf den vor dem Deploy laufenden Stand zurück und beendet sich mit
  Fehlercode; der Auftrag bleibt dann auf dem alten Stand.
- **Manuell**, auf den in Schritt 2 gesetzten Tag:
  ```bash
  cd deploy/firmware-lab
  FIRMWARE_LAB_IMAGE=cads-firmware-lab ./deploy.sh --tag "$ROLLBACK_TAG"
  ./smoke.sh
  ```
- **Nur bei Option B, zusätzlich:** Volume aus der Stream-Sicherung wiederherstellen,
  bevor der Container wieder gestartet wird:
  ```bash
  ssh "$BACKUP_HOST" "sha256sum -c '${BACKUP_PATH}.sha256'"
  ssh service '
    set -e
    docker volume rm firmware-lab-workspace 2>/dev/null || true
    docker volume create firmware-lab-workspace
  '
  ssh "$BACKUP_HOST" "cat $BACKUP_PATH" \
    | ssh service 'docker run --rm -i -v firmware-lab-workspace:/vol alpine tar -C /vol -xf -'
  ```
  Danach den manuellen Rollback (siehe oben) ausführen, damit der Container die
  wiederhergestellten Daten auch mountet.
